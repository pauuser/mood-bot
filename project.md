# Проект: Mood Bot v1.0

## 1. Паспорт проекта

**Участники:** Андрей Тамплон (aatamplon@edu.hse.ru), Павел Иванов (paalivanov@edu.hse.ru)  
**Продукт:** Mood Bot — Telegram-бот для дневника самочувствия  
**Планируемый выпуск:** `v1.0` — Docker-образ и соответствующий ему tag в Git  
**Исходное состояние:** commit [`81ed500`](https://github.com/pauuser/mood-bot/tree/81ed500cb63f5aa1c0aab4403bf3b822d91ea5c6)  
**Репозиторий:** <https://github.com/pauuser/mood-bot>

### Контекст и пользователи

Пользователь отправляет боту `/start`. Каждый вечер бот присылает два вопроса о физическом и психическом самочувствии с кнопками от 1 до 10, а раз в месяц — средние значения.

### Границы

В проект входят код бота, конфигурация, зависимости, Dockerfile, Compose и собранный образ.

### Компоненты, взаимодействия и границы доверия

Бот на Go получает события от Telegram Bot API. На `/start` он сохраняет пользователя в SQLite, на нажатие кнопки — ответ. Две задачи по расписанию рассылают вопросы и статистику. Токен бота передаётся через переменную окружения.

Границы доверия:

- **Telegram → бот.** Текст сообщений и данные кнопок формирует клиент пользователя, поэтому бот не должен принимать их без проверки.
- **Бот → файл БД на хосте.** Ответы хранятся открытым текстом; их читает любой, у кого есть доступ к каталогу `data/`.
- **Внешние компоненты → образ.** В сборку попадают Go-модули, компилятор Go и базовые образы Docker.

### Активы и существенные риски

- **Ответы о самочувствии.** Хранятся вместе с `chat_id`, именем и username. Могут попасть к постороннему или быть искажены. Это личные сведения о здоровье конкретного человека.
- **Токен бота.** Тот, кто его получит, сможет принимать входящие сообщения вместо бота и писать пользователям от его имени.
- **Состав выпуска.** Образ может содержать компоненты с известными уязвимостями.

### Доступные материалы и ограничения

Доступны код, история Git, `go.mod` и `go.sum`, Dockerfile, Compose и конфигурация. Образ собирается, для запуска нужен тестовый бот.

**Конфиденциальность:** в тестах используются только вымышленные данные и отдельный тестовый бот. Токены в репозиторий и отчёты не попадают.

**Почему проект выполним:** в боте около 840 строк на Go. Проверки уже нашли две проблемы, которые можно исправить и перепроверить: устаревший Go и отсутствие проверки ответов.

## 2. Методологическая основа

**Основная рамка:** [NIST SSDF 1.1](https://csrc.nist.gov/pubs/sp/800/218/final)

SSDF описывает практики для всего пути изменения, от кода до выпуска.

**Что ещё рассматривали:**

- [ГОСТ Р 56939-2024](https://protect.gost.ru/gost/details/f3818925-a96f-4f55-96e9-46b44720ee64) рассчитан на организацию-разработчика с формальными процессами и подтверждением соответствия. Для учебного бота это избыточно.
- OWASP SAMM оценивает зрелость организации, а такая задача в проекте не стоит.

Используемые положения:

| Положение SSDF | Что делаем | Признак выполнения |
|---|---|---|
| PO.2 — роли и ответственность | У каждого метода есть ведущий и проверяющий, назначен ответственный за выпуск | Роли записаны в разделе 4, каждый PR одобрен проверяющим |
| PO.4 — критерии проверок | Задаём, какие результаты блокируют выпуск | Правила блокировки в разделе 4 и в workflow |
| PS.3 — сохранение выпуска | К tag `v1.0` прикладываются SBOM и отчёты проверок | Файлы в `evidence/` соответствуют коммиту выпуска |
| PW.4 — проверка сторонних компонентов | govulncheck для Go и модулей, базовые образы по digest | Нет достижимых уязвимостей, для которых есть исправление |
| PW.7, PW.8 — анализ и тестирование кода | Review каждого PR, тесты и фаззинг обработки ответов, `go vet`, поиск секретов | Workflow проходит на коммите выпуска |
| RV.2 — оценка и устранение уязвимостей | Разбор находок: исправить, признать ложной или принять риск с обоснованием | У каждой существенной находки есть решение |

| Проверка | Результат |
|---|---|
| gitleaks 8.30.1, вся история | 0 находок |
| Semgrep 1.177.0, правила для Go, Dockerfile, Compose | 0 находок |

### Существенные разрывы

- **Выпуск собирается на неподдерживаемом Go 1.21.**  
  **Почему важен:** govulncheck нашёл 34 уязвимости стандартной библиотеки, до которых доходит граф вызовов бота. Большая часть приходится на клиент Bot API (`crypto/tls`, `crypto/x509`, `net/http`, `net/url`), через который передаются токен и ответы. Go 1.21 больше не получает исправлений безопасности.  
  **Свидетельство:** отчёты govulncheck [на Go 1.21](evidence/raw-2026-09-27/govet-govulncheck.txt) и [на Go 1.25.14](evidence/raw-2026-09-27/govulncheck-go1.25.14.txt).  
  **Приоритет:** высокий.

- **Бот сохраняет любые данные кнопки как ответ.**  
  **Почему важен:** обработчик не сверяет ответ и текст вопроса с конфигурацией. Тест записал в базу ответы `99999` и `<b>x</b>`, ответ на вопрос, которого нет в конфигурации, и два одинаковых ответа подряд. Статистика считается по всему, что лежит в базе. Можно ли отправить такие данные через Telegram и в чьи чаты, проверим в методе 1.  
  **Свидетельство:** [probe_test.go](evidence/raw-2026-09-27/probe_test.go.txt), тест `TestCallbackStoresAnyData`, [вывод](evidence/raw-2026-09-27/probe-tests.txt).  
  **Приоритет:** средний.

- **Изменения не проверяются перед выпуском.**  
  **Почему важен:** без review и автоматических проверок обе проблемы выше могут вернуться в следующей версии незамеченными.  
  **Свидетельство:** [история Git и данные GitHub API](evidence/raw-2026-09-27/git-history.txt).  
  **Приоритет:** средний.

- **Состав выпуска не фиксируется.**  
  **Почему важен:** без digest базового образа и SBOM нельзя сказать, какие компоненты были в конкретном выпуске.  
  **Свидетельство:** [Dockerfile](https://github.com/pauuser/mood-bot/blob/81ed500cb63f5aa1c0aab4403bf3b822d91ea5c6/Dockerfile).  
  **Приоритет:** низкий.

Ещё две ошибки не относятся к безопасности, но мешают получить работающий выпуск. Сохранённые ответы не читаются из базы (`SELECT *` возвращает 6 столбцов, а `Scan` принимает 5), поэтому статистика никому не приходит ([тест](evidence/raw-2026-09-27/probe-tests.txt) `TestAnswerIsNotReadBack`). На Linux Compose не запускает бота, если каталог `data/` принадлежит root ([воспроизведение](evidence/raw-2026-09-27/compose-chown-linux.txt)). Обе ошибки исправим до выпуска.

## 4. Целевой Secure SDLC

Для каждого выпуска обязательны четыре действия:

1. Изменение попадает в `main` только через pull request. Проверяющий смотрит код и одобряет PR.
2. На каждый PR запускается workflow: `go vet`, тесты, gitleaks и govulncheck.
3. Перед выпуском собирается образ, создаётся SBOM, и основной сценарий прогоняется на тестовом боте: `/start` → вопрос → ответ → статистика.
4. Ответственный за выпуск просматривает результаты и создаёт tag выпуска.

По риску: если PR меняет обработку входящих данных, ведущий метода 1 запускает фаззинг и прикладывает результат к PR.

Проверяющий — участник, который не писал изменение. Ответственный за выпуск — Павел.

**Контрольная точка** — tag выпуска. Его ставят только после успешного workflow и сценария на тестовом боте.

**Выпуск блокируют:**

- найденный секрет;
- достижимая уязвимость, для которой есть исправление;
- упавший тест обработки ответов.

**Исключения** оформляются как issue: причина, компенсирующая мера, ответственный и срок пересмотра, не больше одного выпуска. Если участники не согласны по находке, выпуск откладывается до разбора.

**В рамках курса реализуем:**

- защиту ветки `main`;
- GitHub Actions workflow с четырьмя проверками;
- тесты обработчика кнопок;
- обновление Go;
- закрепление базовых образов по digest;
- SBOM для `v1.0`.

## 5. Технологический профиль

### Метод 1: security-тестирование и фаззинг обработки входных данных

**Риск или свойство:** искажение дневника данными кнопок, которых бот не создавал  
**Цель:** добиться, чтобы сохранялись только ответы из конфигурации на вопросы из конфигурации; проверить, можно ли подделать нажатие через Telegram  
**Область:** `MessageProcessor`, `QuestionRepository`  
**Этап:** проверка изменения (CI) и подготовка выпуска  
**Способ:**

- `go test` с подменой отправки сообщений и временной SQLite;
- фаззинг обработчика встроенным `go test -fuzz`: случайные данные кнопки, текст вопроса и тип чата. Проверяемое свойство: обработчик не падает, а в базу попадают только ответы из конфигурации;
- на тестовом боте — отправка произвольного `callback_data` через клиентскую библиотеку MTProto (Telethon), а также ответы из группового чата.

**Ведущий:** Андрей  
**Проверка партнёром:** запуск тестов из чистого checkout и проверка, что обычный ответ по-прежнему сохраняется  
**Свидетельства:**

- тесты и fuzz-тест в репозитории, найденные фаззером входы в `testdata/fuzz/`;
- `evidence/callback-before.txt` и `evidence/callback-after.txt`;
- протокол проверки на тестовом боте.

**Не покрывает:** доступ к файлу БД на хосте и чтение данных из логов

### Метод 2: анализ состава ПО (SCA) и SBOM

**Риск или свойство:** известные уязвимости в Go и модулях, неизвестный состав образа  
**Цель:** устранить достижимые уязвимости обновлением Go и модулей и зафиксировать состав `v1.0`  
**Область:** `go.mod`, `go.sum`, Dockerfile, собранный образ  
**Этап:** каждый PR и сборка выпуска  
**Способ:** govulncheck 1.1.4; SBOM в формате CycloneDX; базовые образы по digest  
**Ведущий:** Павел  
**Проверка партнёром:** повторный запуск govulncheck на коммите выпуска и сверка SBOM с `go.mod`  
**Свидетельства:**

- [отчёт до обновления](evidence/raw-2026-09-27/govet-govulncheck.txt) — 34 достижимые уязвимости;
- `evidence/govulncheck-v1.0.txt`;
- `evidence/sbom-v1.0.json`.

**Не покрывает:** пакеты Debian в итоговом образе и уязвимости, которых ещё нет в базе Go
